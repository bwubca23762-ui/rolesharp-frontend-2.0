## Method — read this first

I did **not** read all 36,724 lines individually. What I actually did:

1. Copied the source to local disk (the mounted drive was too slow for full-tree tooling — this is why the earlier lint attempt timed out twice)
2. Ran **ESLint across the entire tree** and TypeScript compilation to completion
3. Ran **16 targeted bug-class scans** across every source file — silent failure handlers, N+1 queries, unbounded selects, listener/timer leaks, XSS sinks, migration idempotency, env bypass, accessibility, dead markers, type escapes
4. **Read in full** every file a scan flagged, to confirm or reject the hit

Every finding below was confirmed by reading the actual code. **Two heuristic hits turned out to be false positives and were dropped** — they are documented at the end so you can see what the scans over-reported.

### C2 — Leaked interval + false success message in the blog generator

`app/admin/admin-panel.tsx:1119-1124`:

```ts
let tries = 0;
const iv = setInterval(async () => {
  tries++;
  await load();
  if (tries > 30) { clearInterval(iv); load(); setMsg({ ok: true, text: "Published! See it below." }); }
}, 8000);
```

This sits inside an **async click handler, not a `useEffect`**. Two distinct defects:

**C2a — Timer leak.** There is no unmount cleanup. The interval runs for 30 × 8 s = **4 minutes**. Any admin who switches tabs before it finishes leaves a detached interval calling `load()` every 8 s — repeated `fetch` plus `setPosts()` on an unmounted component. React will warn; the requests are real load. Nothing ever clears it if the component is gone, because `clearInterval` only runs inside the callback's own success branch.

**C2b — The success message is a lie.** After 30 ticks it announces `"Published! See it below."` **unconditionally** — it is a fixed timer, not a check of whether the post exists. If generation failed, the admin is told it succeeded. Nothing inspects the result of `load()`.

The UI also promises *"~60-90 seconds"* while the handler says *"~2-3 minutes"* and actually waits 4.

**Fix:** move the polling into a `useEffect` with cleanup, poll until the slug actually appears, and cap with a real timeout that reports failure honestly.

## High

### H1 — `getPost()` loads the entire blog table to fetch one post

`lib/blog.ts:62-65`:

```ts
export async function getPost(slug: string): Promise<BlogPost | null> {
  const db = await dbPosts();
  return db.find((p) => p.slug === slug) ?? FILE_POSTS.find((p) => p.slug === slug) ?? null;
}
```

`dbPosts()` runs:

```sql
select data from blog_posts where status='published' order by created_at desc
```

**No `LIMIT`, no `where slug=…`.** Every blog post page render pulls **every published post's full JSON body** out of Postgres, deserializes all of them, then does an in-memory `.find()` to keep one.

This matters because the cost grows on its own: `saveGeneratedPost()` plus the `rolesharp-blog-worker` systemd unit means an AI generator is continuously adding rows. Cost per page view scales linearly with total posts, forever.

**Fix:**

```sql
select data from blog_posts where slug=$1 and status='published' limit 1
```

`listPosts()` has the same unbounded shape and is called by the sitemap, blog index, and related-posts. That one legitimately needs breadth — but it should be paginated or cached before the table gets large.

### H2 — 50 empty catch blocks

```
$ grep -rcE 'catch\s*(\([^)]*\))?\s*\{\s*\}' app lib worker scripts
50
```

Concentrated in `app/admin/admin-panel.tsx` (8), `app/build/page.tsx` (6), `app/checker/page.tsx` (2), `app/student-banner.tsx` (2).

**A meaningful share are legitimate** — `try { localStorage.setItem(...) } catch {}` correctly guards against Safari private-mode quota errors, and I am not counting those against the code.

The ones that matter are network calls, e.g. `admin-panel.tsx:1104`:

```ts
try { const r = await fetch("/api/admin/blog"); const j = await r.json().catch(() => ({})); if (r.ok) setPosts(j.posts || []); } catch {}
```

If this fails the admin sees an empty list with **no error, no spinner, no retry** — indistinguishable from "there are no posts". Combined with the total absence of error tracking (see the first audit), these failures are invisible in both directions: the user isn't told and neither are you.

**Fix:** separate the two cases. Keep bare `catch {}` for storage guards; every network catch should set visible error state.

## False positives — what my scans over-reported

Included so you can calibrate how much to trust the numbers above.

**`app/session-watch.tsx` — flagged as a listener leak. It is not.** My heuristic counted *lines* containing add/remove calls; line 39 does both in one line, so it read as 2 adds / 1 remove. Reading it, the cleanup is textbook:

```ts
return () => { stop = true; clearInterval(iv); document.removeEventListener("visibilitychange", onVis); };
```

It also sets a `stop` flag so an in-flight `fetch` cannot act after unmount. This is *more* careful than required.

**14 "unbounded query" hits — 12 were `where id=$1` primary-key lookups.** Correct by construction. Only the two in `lib/blog.ts` (H1) are real.

## Limits of this audit

- **The six test suites still have never run** (esbuild platform mismatch). No claim here depends on test results.
- **No runtime execution.** No database, Redis, or LLM endpoint was available. Concurrency, cache behaviour, and queue correctness were assessed by reading code. The migration-idempotency finding is from static inspection of SQL, not from actually running them twice.
- **Not every line was read.** 16 systematic scans covered all 958 files; flagged files were then read in full. A logic bug in a file that tripped no scan would not appear here.
- **`public/` was excluded** from the local copy for speed — no assets were reviewed.
