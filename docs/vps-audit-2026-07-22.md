# RoleSharp production VPS audit

Audit date: 2026-07-22

Method: read-only service, network, TLS, firewall, process, database, backup, deployment, and log inspection.

## Executive result

The host is operational and has ample capacity. The web, worker, jobs, PostgreSQL, Redis, Nginx, Docker, firewall, Fail2ban, and automatic-upgrade services were active, with no failed systemd units or application warnings in the inspected 24-hour window. The main risk is deployment drift: production predates the latest security commits and database migration.

## Findings

### High — current security release is not deployed

- Production lacks migration `024_account_deletion.sql` and the new deployment guard.
- The deployed foreign key still uses `NO ACTION`, confirming migration 024 is not applied.
- `ADMIN_TOTP_SECRET` is not configured, so the deployment guard correctly blocks a new release.

Remediation: configure admin TOTP through the protected VPS secret-management process, verify an authenticator code, then deploy the current commit and migrations. Never paste the secret into chat or commit it.

### Medium — origin bypasses Cloudflare

- Ports 80 and 443 accept traffic from the public internet.
- A direct origin request with the RoleSharp host name reaches the application.
- The origin certificate is long-lived and self-signed rather than a scoped Cloudflare Origin CA certificate.

Remediation: after confirming Cloudflare proxy health and an emergency access path, restrict origin web ports to current Cloudflare IP ranges and use an Origin CA certificate. Automate range refresh; stale static ranges can cause an outage.

### Medium — packages await security/maintenance updates

Pending updates include Nginx and several system libraries. Cloudflared also reports a newer release.

Remediation: take a fresh backup, schedule a maintenance window, apply updates, reboot if required, and rerun endpoint/TLS checks.

### Medium — backups are local only

- Daily PostgreSQL dumps exist with seven-day retention and plausible increasing size.
- No off-host, encrypted copy or restore-test record was found.

Remediation: add encrypted off-site storage, checksum verification, alerting, and a scheduled restore drill. A backup is not proven until it can be restored.

### Low — information and permission hardening

- The direct origin disclosed the Nginx version.
- Service units did not set a restrictive umask.
- PostgreSQL and Redis containers have no explicit memory/PID caps or read-only hardening.

Repository remediation included `server_tokens off` and `UMask=0027`. Container limits should be load-tested before production rollout because overly small limits can interrupt database recovery or background jobs.

## Verified healthy controls

- Application, database, cache, and proxy services bind to loopback where appropriate.
- UFW defaults to deny incoming traffic and blocks public application/database/cache ports.
- SSH root login is key-only; interactive keyboard authentication is disabled.
- Fail2ban is active and has blocked sustained login attempts.
- TLS 1.0/1.1 fail; TLS 1.2/1.3 work.
- Public responses include HSTS, CSP, frame, MIME-sniffing, referrer, permissions, COOP, and CORP headers.
- Systemd services run as the non-root `rolesharp` user with `NoNewPrivileges`, `PrivateTmp`, `ProtectHome`, and strict `ProtectSystem` controls.
- Host memory, swap, and disk headroom are healthy.

## Release gate

Do not describe production as fully fixed until all of these pass:

1. Admin TOTP is configured and tested.
2. Current commit and migrations 024–025 are deployed.
3. Public and direct-origin behavior is rechecked.
4. Database backup catalog validation and a restore drill succeed.
5. Smoke tests cover landing, builder, checker, jobs, pricing, authentication, country API, and health endpoints.
